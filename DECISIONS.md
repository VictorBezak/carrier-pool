1. (USER) When the shared carrier pool is activated, if 2 brokers have history with the same carrier, each broker will continue to only see their history with that broker. The only difference will be that if the other brokers participating in the pool have data for carriers that the other broker does not have any history with, then that carrier data will begin showing for the other broker for the first time. So if there is overlap, then the broker continues to see only their history with the carrier, but if there is no overlap and the carrier is completely unknown to the broker, then it will begin showing. Of course, this is while continuing to respect our constraint that broker data can not leak to other brokers -- if they opt-in to the shared carrier pool, then they will only be sharing data for those carriers.

2. (AGENT) BrokerOS carrier account records in the documented TMS C export do not include MC/DOT identifiers. Cross-system carrier identity in the synthetic data is therefore only provable between FreightFlow and HaulDesk, where those fields exist in the provided schemas. BrokerOS carriers should not be matched into a shared carrier pool by invented authority fields.

3. (AGENT) Carrier ranking is implemented as a deterministic fit score, not an acceptance-probability model. The broker TMS feeds record bookings, rates, locations, appointment actuals, corrections, and carrier changes; they do not record which carriers were called, tendered, rejected, or unavailable. The score therefore prioritizes carriers to contact using observable historical fit: similar-lane familiarity, positioning/deadhead, shrunk price history, appointment reliability, recent relationship activity, customer affinity, and rate/fall-through stability.

4. (AGENT) Lane matching uses ZIP centroid distance kernels rather than city/state buckets. Direct lane evidence is weighted by origin and destination proximity; reverse-lane evidence is allowed but discounted. This avoids treating all TX-to-TX loads as equivalent while still letting Grand Prairie/Katy history inform Arlington/Sugar Land.

5. (AGENT) Small-sample carrier statistics are shrunk toward broker-local priors instead of trusting raw averages. Price uses a k=4 prior; reliability uses a four-observation Beta-style prior; customer affinity is heavily shrunk. Confidence is calculated separately from score so a high-fit carrier with thin evidence can be shown as low or medium confidence.

6. (AGENT) Tenant isolation is structural in the ranker: feature statistics are keyed by `(broker_id, carrier_id)`. MC/DOT is identity metadata only and is not used to blend performance across brokers. This preserves the user's shared-pool rule that an overlapping carrier remains evaluated from the requesting broker's own history.

7. (AGENT) The ranker is now exposed through a small platform: Postgres records an append-only `load_version` log plus a `sync_file` watermark, `carrier-pool-sync` ingests one TMS sync file at a time in global chronological order, FastAPI replays the canonical store from the database, and the React frontend shows active loads, expected carrier cost, ranked carriers, reasons, limitations, component evidence, price comparables, and the version/as-of trail. Corrections are not patched into derived aggregates; a later sync creates a later version and the as-of projection is recomputed. The shared carrier pool is a separate tier, not blended into broker-local rankings. Its crossing payload is a fixed allowlist of derived/bucketed carrier fields (`carrier_name`, MC/DOT, optional home city/state, equipment buckets, ZIP3 lane buckets, on-time band, recency band); no rates, customers, load IDs, source files, exact counts, ZIP5s, timestamps, or raw TMS payloads cross broker boundaries. At the current corpus size this is intentionally simple and easy to audit. At millions of loads, the next step would be materialized per-broker/per-lane feature tables that can be invalidated from the affected load-version keys rather than replaying the whole broker.

8. (AGENT) ZIP coordinates come from the 2020 US Census Gazetteer ZCTA file (all 33,144 national ZCTAs, `INTPTLAT`/`INTPTLONG` interior points), vendored at `backend/src/carrier_pool/reference/zcta_centroids.csv` and rebuildable via `python3 -m tools.geo.build_zcta_reference`. The Gazetteer is a US federal government work in the public domain, so the trimmed table is committed directly. It is vendored rather than fetched at runtime so the ranker stays hermetic and testable offline. This replaces an earlier hand-authored 17-row table whose coordinates were copied from the generator's own `PLACES` roster; that arrangement was circular, since the ranker's geography was defined by the same table used to synthesize the data it ranked. The generator now reads the same vendored file, so one external authority defines geography for both sides.

9. (AGENT) ZCTAs are not USPS ZIP codes. ZIPs that exist only as PO boxes or single-building business codes have no ZCTA, so `GeoIndex` falls back to the centroid of the ZIP3 prefix, which locates a shipment to within a sectional center. A few prefixes are entirely point-ZIPs (73301, the IRS in Austin, is the standard example) and cannot be located at all; those return infinite distance rather than raising, which zeroes every `exp(-d/k)` decay so the carrier simply earns no geographic credit instead of aborting the ranking. Production should upgrade the fallback with a maintained ZIP-to-ZCTA crosswalk.

10. (AGENT) Every generator `Place` needs a distinct ZCTA, because two places sharing one ZIP collapse to a single point for any ZIP-keyed consumer. Schertz and Selma genuinely share 78154, so the roster substitutes Cibolo (78108), a distinct neighbouring ZCTA in the same metro.

11. (AGENT) The frontend is built as a single-tenant dashboard, not a multi-broker demo. An earlier pass put the three brokers in top-level tabs, which framed the product as a tenant switcher and made it easy to miss that each answer is derived from one broker's data alone. Broker impersonation, as-of replay, pool opt-in, and the request log now sit behind a visually quarantined "Dev tools" sheet in the corner, so the default reading of the app is one broker's coverage desk. The dev sheet is deliberately not gated on `import.meta.env.DEV`: reviewers run the production Docker build, and hiding the tenant switcher there would remove the fastest way to check that data does not leak across brokers. In a real deployment the broker comes from the session and that sheet ships behind an internal-role flag.

12. (AGENT) UI is assembled from shadcn/ui components over Tailwind v4 rather than hand-written CSS. The only stylesheet is the generated `frontend/src/index.css`, which carries the Tailwind import and the theme variables; component styling is utility classes on registry components. The two elements with no registry equivalent are the weighted-contribution bar in the ranked-carrier table (each segment is one scoring component's `weight x score`, so the bar's total length is the carrier's score and its composition is the explanation) and the lane-trace SVG, whose historical lanes are fanned out on curves because a carrier's history usually runs the same corridor as the load and would otherwise collapse onto the target line.

13. (AGENT) `repository.brokers()` counted a load as awaiting coverage if any of its versions had ever been `ACTIVE`, so the API reported 22 active loads for a broker that had 3. Counts now resolve the current version per load with `distinct on (broker_id, raw_load_id) ... order by synced_at desc`, matching how `CanonicalStore` decides which version is current, so file mode and database mode agree. A DB-gated test asserts the counts against the file store rather than a fixed number.

14. (AGENT) As-of replay projects the whole read path, not just the ranking. `as_of` was originally threaded only into `/recommendation`, so the load list and load detail always served the current version of every load. The board therefore rendered live rows, statuses, rates and margins no matter where the replay slider sat, and it asked for recommendations on loads whose live status was `ACTIVE` — loads that in this corpus first appear in the last few syncs — so most slider positions returned `404 Load ... was not known at ...` for every row and the page silently degraded to "unavailable" cells. `/loads` and `/loads/{id}` now take the same `as_of` and resolve through `CanonicalStore.loads_as_of`, and the version trail on the detail page is truncated at the cutoff. The rule is that a replayed page shows the book exactly as that broker's TMS had it at that sync, including loads that were still awaiting coverage and rates that were later corrected; nothing in the broker-facing UI is special-cased for replay being active.
